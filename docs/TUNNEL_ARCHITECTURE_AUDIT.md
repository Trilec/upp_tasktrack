# Verdict

**CHANGE NOW**

Keep the machine-level runtime and separate MCP services. Do not ship the current supervision and credential implementation unchanged. Native channels are a good routing boundary; they currently do **not** provide the failure isolation the architecture expects.

# Change Now

1. **High — one stdio child can stop every service.** Upstream `stdio_command.go` calls the application shutdowner on unexpected exit, stdout EOF or stdin failure; its channel factory passes the same lifecycle/shutdowner to every channel. TaskTrack has no restart policy. Killing PatchTrack can therefore stop TaskTrack too. **Direction:** retain native channels, but obtain a runtime change making child failure channel-local, with bounded restart/backoff and explicit unavailable status. Never automatically replay an interrupted mutation. If that change is unavailable, independently supervised loopback HTTP MCP services are a concrete alternative to evaluate; an aggregator does not inherently solve this. Until fixed, document the runtime as one shared failure domain. [Upstream transport](https://github.com/openai/tunnel-client/blob/9f77746a5498289f04e1ae6d3e0c830f3871af52/pkg/mcpclient/stdio_command.go), [channel factory](https://github.com/openai/tunnel-client/blob/9f77746a5498289f04e1ae6d3e0c830f3871af52/pkg/mcpclient/stdio_command_factory.go).

2. **High — the plaintext launch file has neither guaranteed short lifetime nor reliable cleanup.** `McpTunnelRuntime.cpp:CreateSecretFile` writes before POSIX `chmod`, ignores permission failure, and specifies no Windows ACL. A failed `SaveFile` forgets the path even if a partial file remains. `DeleteSecretFile` forgets it even when deletion fails. After the four-second startup loop, a live runtime without a health URL retains the file indefinitely; a manager crash bypasses cleanup entirely. **Direction:** replace it with the bounded anonymous-pipe handoff below. While retaining RC compatibility, use exclusive creation with restrictive permissions from creation, checked writes/deletion, retained cleanup ownership, and a hard startup deadline. Unlinking is not secure erasure on SSDs/backups.

3. **High — ambient environment can change where the key goes.** `McpTunnelBuildChildEnvironment` removes three key names but copies everything else. Upstream accepts `CONTROL_PLANE_BASE_URL`, profile-file selectors and unsafe logging settings from that environment. An inherited development endpoint can receive the runtime bearer key; ambient configuration can also alter effective routing. Arbitrary unrelated secrets still reach every MCP child. **Direction:** construct a minimal runtime environment; explicitly approve endpoint, proxy/CA and logging configuration, disable raw HTTP logging, and prevent ambient profile overrides. Provide per-service environment/credential references rather than a machine-wide bag of secrets. This prevents accidental exposure; same-user malicious code remains outside this isolation guarantee. [Configuration resolver](https://github.com/openai/tunnel-client/blob/9f77746a5498289f04e1ae6d3e0c830f3871af52/pkg/runtimeconfig/config.go).

4. **High — credentials are not actually bound to profiles.** `TaskTrackTunnelManager.h:session_api_key_` is one global `String`; `ReadCredential`, `SetCredential` and `ClearCredential` operate on it regardless of profile identity. Duplicating a profile clears its tunnel ID but silently retains access to the same session key. There is no credential-reference field despite documentation describing a new reference. **Direction:** introduce opaque credential IDs now, with explicit profile/tunnel binding. Duplicates start unbound. Changing tunnel identity invalidates or explicitly rebinds the credential; changing runtime executable is also a trust-relevant action because that executable receives the key. Keep the environment mode an explicit automation override.

5. **High — stop/crash ownership is incomplete.** `Stop()` calls only `LocalProcess::Kill`; there is no process-tree container or interprocess ownership lock. The installed U++ `E:/upp-18468/uppsrc/Core/LocalProcess.cpp:393` uses `TerminateProcess` on Windows, bypassing upstream graceful hooks, and POSIX SIGTERM followed by an unbounded wait. Children/grandchildren can outlive the supervisor, and two managers can run the same profile. **Direction:** enforce one owner per intended machine/user scope using an OS-backed lock; use a Windows kill-on-close Job Object with assignment before children can spawn, and a POSIX process group plus parent-death/watchdog strategy. Implement graceful stop, bounded wait, then tree termination. Define whether launched TaskTrack UI windows belong to that lifetime. Release ownership only after termination is confirmed. A hostname is a display/default value, not an ownership lock or stable unique machine identity.

6. **Medium — readiness and UI scheduling overclaim availability.** `Start()` sleeps up to four seconds on the GUI thread; each timer `Refresh()` can add two synchronous two-second HTTP timeouts. No startup deadline or crash recovery exists. `Refresh` clears errors whenever liveness succeeds, losing readiness failure reasons; upstream readiness checks startup probe/OAuth state, not successful ongoing control-plane polling. **Direction:** use one cancellable supervisor worker with immutable status snapshots/run-generation IDs; separate process alive, local readiness, control-plane connectivity and per-service availability. Add explicit startup timeout and bounded opt-in crash restart, excluding persistent auth/config errors. Let upstream handle network reconnect; on resume refresh state and mark connectivity unknown until re-established. Validate the health URL as loopback HTTP with no credentials/query/redirect escape, consume it for the current run only, and bound reads. Unique per-start files already reduce ordinary stale-port reuse; they do not prove endpoint identity. [Readiness implementation](https://github.com/openai/tunnel-client/blob/9f77746a5498289f04e1ae6d3e0c830f3871af52/pkg/runtimehealth/health.go).

7. **Medium — profile compatibility is permissive and lossy.** `LoadProfiles` accepts future schema versions and silently resets malformed state; `SaveProfiles` rewrites schema 2 using unchecked, non-atomic `SaveFile`. Older software can destroy newer configuration. `IsCanonicalChannel` accepts dots, uppercase and unbounded length; upstream canonicalizes case and accepts only `[a-z0-9_-]{1,64}`, so `foo`/`FOO`, `HARPOON`, dots and long names defeat local preflight. **Direction:** reject unknown schemas without rewriting, validate types and unique profile IDs, perform explicit migrations, and atomically replace with recovery on write failure. Match the pinned runtime's canonical channel contract and reserved-name checks. Keep exactly one enabled `main` for this product. [Channel rules](https://github.com/openai/tunnel-client/blob/9f77746a5498289f04e1ae6d3e0c830f3871af52/pkg/types/channel.go).

8. **Medium — saved runtime selection is overwritten at startup.** `TunnelApp/main.cpp:29` always supplies a default executable path; the manager constructor then treats it as an explicit override of the selected saved profile. Restarting can silently switch binaries or break auto-connect. **Direction:** distinguish absent CLI override from a default used only for new/missing configuration. Record and verify the supported runtime version/artifact; source VERSION equality alone does not establish bundled binary parity.

# Credential / Vault Recommendation

**Ship one portable passphrase-unlocked, authenticated encrypted vault containing multiple credential records, with a separate neutral credential-provider interface.** This protects a copied vault and offline backups. It does not protect an unlocked process against administrator access, malware running with equivalent access, or arbitrary MCP programs sharing that account.

**Layout and identity.** Use a random vault UUID and random entry UUIDs, never key substrings or hashes of tunnel names as identifiers. Encrypt each record's runtime key, tunnel identity, profile/machine binding, credential purpose, generation and timestamps together inside one authenticated payload. Keep only format/KDF identifiers and parameters, random salt/nonces, vault UUID, wrapped data key and ciphertext/tag outside. Ordinary profile configuration can retain a local display label, opaque profile/machine IDs, service bindings and an opaque credential reference. Avoid duplicating tunnel IDs outside the vault when privacy matters; if the UI/config needs a plaintext copy, treat it as nonsecret metadata and verify it against the authenticated record before launch. Encryption alone must not allow a key to be silently paired with a different tunnel.

**Unlock and cryptography.** A strong user master passphrase derives a key-encryption key using PBKDF2-HMAC-SHA256 with a fresh random salt of at least 16 bytes. That key wraps a random 256-bit data-encryption key; AES-256-GCM encrypts the vault payload, with fresh 96-bit nonces and full 128-bit tags for every encryption. Authenticate the versioned header/context as associated data and release no plaintext before tag verification. Use bounded parsing, atomic replacement, a writer lock and encrypted recovery backups. Do not invent a streaming encryption format.

PBKDF2 is acceptable for this U++-based design with a strong passphrase, although Argon2id offers better memory-hard resistance. Set an explicit floor of 600,000 SHA-256 iterations and benchmark upward toward roughly 0.5–1 second on supported hardware; persist parameters and upgrade after successful unlock. This latency target is a product recommendation, not a security proof. Bound hostile KDF parameters before evaluation. [OWASP's current work-factor guidance](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html#pbkdf2).

Do not assume the installed U++ API is the newer API described in the proposal: the inspected local `Core/SSL/SSL.h` defaults to 100,000 iterations, caps at 1,000,000, and exposes `String` password interfaces. Pin and verify the dependency that actually supplies SecureBuffer/SecureZero and the required authenticated format; do not silently accept a clamp if calibration exceeds the cap. Passphrase changes rewrap the data key. A compromised data key requires payload re-encryption with a new key. No plaintext unlock-key file sits beside the vault. No forgotten-passphrase recovery is promised; recreate/revoke credentials if the passphrase is lost. SSH keys/agents add identity-format, signing and availability complications without solving this application's basic unlock problem, so I would not use them as the primary mechanism. Optional keychain adapters can wrap the same data key later. Unattended restart after a reboot requires an explicit external unlock provider or the existing automation credential source.

**UI.** Show `Stored · <12 hex SHA-256 fingerprint characters>` after unlock; show `Stored (locked)` when locked. Hash a domain-separated full high-entropy API key, not its literal last four characters. The fingerprint is an operator comparison hint, not an authentication value; keep it in the encrypted record to avoid unnecessary cross-vault correlation. Never offer retrieval/reveal of a stored key. The present visibility toggle exists only in the entry dialog; removing it after entry is essential, while allowing deliberate reveal during entry is a separate UX choice.

**Memory audit.** The current path is `UiPasswordEdit` → `GetTextUtf8`/`TrimBoth` temporaries (including validation) → `session_api_key_` → `ReadCredential`/local `String secret` → `Start(const String&)` → file write. U++ strings can share backing storage; these are retention points, not necessarily independent byte allocations. `Clear()` and ordinary destruction are not guaranteed zeroization. Environment mode also creates `GetEnv` values repeatedly during availability projection and retains the original manager environment. Use owned noncopyable SecureBuffer storage and byte-span APIs, wipe replaced/cleared session keys, entry/cancel buffers, KDF/passphrase material and launch buffers on every exit path. Audit unavoidable UI/UTF-8 and crypto-library copies rather than assuming a secure outer container fixes them.

The three named OpenAI key variables are excluded from the constructed runtime environment. There is no intentional key value in argv/profile JSON or `BuildDiagnostics`; `CopyDiagnostics` copies that summary, not the raw runtime log. However, `DrainOutput`/`GetDiagnostics` accept unredacted runtime output and logs, and error dialogs append them. Upstream forwards MCP stderr and logs configured commands: service arguments must never contain credentials. Disable raw HTTP logging and bound/rotate diagnostic files; tailing 3 KB after loading the entire file does not bound memory or disk usage. The application's input clipboard is not cleared; do not silently erase unrelated clipboard content, but offer explicit clearing of the just-pasted secret. SecureZero reduces residual copies; claims of erasing allocator history, swap, crash dumps or Go/TLS internals would be security theatre.

**Runtime handoff — preferred design.** Add explicit upstream `--control-plane.api-key stdin-once` support, backed by an inherited anonymous pipe connected to runtime stdin. The manager already uses LocalProcess pipes; MCP children get separately created stdio pipes. Read a small bounded key once, enforce a timeout/EOF contract, reject malformed/oversize input, close the read endpoint before starting MCP children, and wipe the temporary read buffer after constructing the necessary runtime credential. Parent closes its duplicate read handle, writes once, closes its writer and wipes its launch buffer. Use byte-exact writes with charset conversion disabled. Whitelist inherited handles on Windows. Never echo the secret or fall back silently to environment/file on failure. This changes key input, not the tunnel wire protocol.

At the inspected upstream revision, the key-reference API supports **only `env:` and `file:`**, with fallback environment names; there is no explicit stdin-once, fd, inherited Windows handle, named-pipe or general IPC secret resolver. `file:` uses `os.ReadFile`, so on POSIX `file:/dev/stdin` or `/dev/fd/N` can read an inherited pipe where those paths exist; a FIFO similarly has a filesystem name but kernel-buffered contents. These are platform-dependent compositions, not a portable promised interface. A Windows named pipe through `file:` needs testing against Go open/read/EOF behavior plus restrictive ACLs and race handling; it is not established here as supported. A dedicated `fd:`/`handle:` API is viable if stdin later has another role, but adds platform-specific launcher plumbing without a present benefit. [Actual resolver](https://github.com/openai/tunnel-client/blob/9f77746a5498289f04e1ae6d3e0c830f3871af52/pkg/runtimeconfig/config.go).

| Mechanism | Risk in this process tree |
| --- | --- |
| Environment | Avoids a plaintext file, but upstream stdio `exec.Command` leaves `cmd.Env` nil: MCP children inherit the runtime environment. Clearing the parent's copy after spawn cannot fix that. |
| Temporary regular file | Keeps the key out of child environments, but introduces ACL, persistence, crash and deletion-failure exposure; current cleanup is insufficient. |
| Anonymous pipe / inherited handle | No named secret file or secret environment entry; brief kernel-buffer lifetime and explicit endpoint ownership. Consume/close before MCP spawn to prevent inheritance. Preferred. |

A pipe eliminates the disk-backed launch file, not all runtime plaintext: the upstream config holds a Go string, and HTTP authentication requires the key while reconnecting/polling. Locking the manager vault does not erase an already running runtime's credential; stopping it is required for that boundary.

**Rotation.** Replace the bound record atomically, advance its generation, and restart the runtime with the new key; verify a real control-plane operation before revoking the old key. Local readiness alone is insufficient. Clear removes the binding and ciphertext record, wipes unlocked memory, and stops the active runtime if immediate withdrawal is intended. Local deletion is not upstream revocation and cannot erase encrypted historical backups. Duplicates never inherit credential bindings implicitly.

# Future Improvements

- Keep `McpTunnelRuntime` as the transport/supervision boundary. Its schema-1 migration currently embeds TaskTrack names and `mcp_path`; move that compatibility adapter to TaskTrack when touching migration. Generic profile storage and credential resolution still live in the TaskTrack manager and should become neutral components before a second product owns the manager. TaskTrack probe/activity and default-service seeding correctly remain application adapters; no TaskTrack business logic belongs in the runtime.
- Keep `machine/profile → services[] → channel bindings`; several trusted services fit it well. Channels are neither sandboxes nor fairness guarantees: the shared runtime/dispatcher is a resource and failure domain. Separate OS identities/process supervision when services need different trust or availability guarantees. Do not make “one machine runtime” an irreversible prohibition on those deployments.
- Keep OAuth authorization policy and user/token lifecycle with the service/connector. The control-plane runtime API key remains separate; OAuth does not replace it. Reserve typed service transport/auth configuration and purpose-scoped credential references, so future HTTP OAuth forwarding/discovery can map to upstream support without merging domains. Current command-only services have no per-request HTTP authorization hop. [Official architecture/auth boundaries](https://github.com/openai/tunnel-client/blob/9f77746a5498289f04e1ae6d3e0c830f3871af52/docs/architecture.md).
- Defer a gateway, generic plugin framework, mandatory OS keychain and SSH unlock. There is no demonstrated need for aggregation. If the real connector cannot address named channels, revisit deployment/routing on that evidence before building more services.
- TaskTrack activity files use global paths beside executables and unlocked read/modify/write. Namespace and atomically update them if multiple TaskTrack instances are supported; do not present them as machine-wide or security-audit telemetry.

# Missing Validation

Minimum release gate, using dummy credentials and controllable subprocesses wherever possible:

1. **Pinned binary and routing:** run Windows `verify.ps1` against current dependencies, then real-account calls to distinct `main` and second-channel services with identical tool names and distinct responses. Prove product-side channel addressing and no cross-routing. Current tests prove argument strings only.
2. **Runtime contract table:** zero/two/disabled `main`, reserved names in mixed case, case-colliding channels, dots, 64/65-character boundary, supported channel-count limit, spaces/quoting in commands and malformed tunnel ID. Compare preflight to the pinned runtime parser. Existing `tunnel_test` fixtures are not valid upstream tunnel IDs.
3. **Failure and containment:** child exit/EOF, failed child launch, runtime exit before/after health publication, hung startup, repeated start/stop and manager force-kill with grandchildren. Assert bounded shutdown, no orphans/handle leaks, one-owner locking and surviving service availability after the isolation change. Cover Windows and POSIX behavior.
4. **Health/recovery:** live health with rejected runtime key, blocked poll route, failed service initialization, stale/hostile URL file, disconnect/reconnect and suspend/resume. Assert no false connected state, responsive Stop, bounded retry and no replay of uncertain mutations.
5. **Secret path:** seed distinctive dummy secrets in the test environment; capture actual runtime/MCP argv, environment and diagnostic output. Exercise partial write, denied delete, failed spawn and manager crash while the RC file path remains. For pipe handoff test timeout, EOF, oversize input, child handle inheritance and no secret file creation. Existing environment tests can pass without any secret being seeded; the `test-secret` argv assertion never supplies that value.
6. **Profiles/vault:** session-key separation across select/duplicate/delete/tunnel rotation; saved executable survives reopening. Schema-1 migration, unknown version preservation, corrupt/truncated input and interrupted writes. Before durable vault release: wrong passphrase, modified header/ciphertext/tag, nonce uniqueness, bounded KDF parameters, replace/clear/rewrap and encrypted-backup recovery. Review the exact U++ crypto dependency; no custom cryptographic construction should bypass this gate.

# Final Answers

1. **Would I keep it?** Yes to the core architecture; **CHANGE NOW** for the implementation and the failure-isolation claim.
2. **Immediate changes?** Channel-local failure handling, bounded process-tree supervision, controlled environment/configuration, profile-bound credentials, pipe handoff, truthful asynchronous health, strict persistence/channel validation and the saved-runtime override fix.
3. **Deliberately unchanged?** Separate domain services/persistence/tool contracts, official tunnel wire implementation, native channels, exactly one enabled `main`, and optional session/environment RC inputs. No speculative gateway.
4. **Right abstraction?** Yes. Move generic storage/credential concerns out of the TaskTrack UI as they grow; keep legacy migration and TaskTrack telemetry in adapters.
5. **Vault I would ship?** One versioned AES-256-GCM vault, random wrapped data key, strong passphrase/PBKDF2 unlock, opaque bound entries, short hash fingerprints and controlled secret memory.
6. **Cleanest file elimination?** Upstream `stdin-once` via an inherited anonymous pipe consumed and closed before any MCP child starts. Environment alone fails the inheritance requirement; platform-specific `file:` pipe tricks need explicit qualification.
7. **Likely 1–3-year harm?** Treating channels as independent security/availability boundaries, sharing ambient credentials/configuration, or hard-coding command-only transport and one global key. The machine/profile/service model itself is sound and needs no architectural replacement.
