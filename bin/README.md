# TaskTrack runtime bundle

`bin/` is the **staged runtime boundary**, not compiler output.

- `build/` (or a separate `verify.ps1 -OutputDir`) is disposable engineering output.
- `bin/<platform>/` is generated by `stage-bin.ps1` and contains only the executables and notices needed to run/copy TaskTrack.
- Generated platform directories are intentionally ignored by Git. Do not commit binaries from `bin/`.

For the current Windows build:

```powershell
.\verify.ps1 -UppRoot C:\upp -OutputDir .\build-release
.\stage-bin.ps1 -BuildDir .\build-release
```

This creates `bin/windows-x64/`.

The staged production set is:

```text
TaskTrackMcp.exe
TaskTrackGui.exe
TaskTrackDashboardGui.exe
TaskTrackTunnelGui.exe
tunnel-client.exe
README.txt
manifest.json
LICENSE-TaskTrack.txt
third-party/openai-tunnel-client/...
```

The OpenAI runtime is copied from the local `tunnel-client/` source artifact and
renamed to `tunnel-client.exe`, which is the tunnel manager's same-directory
default. `stage-bin.ps1` verifies the vendor SHA-256 against
`tunnel-client/runtime-manifest.json` before copying it.

Do not place runtime API keys, vault files, profile JSON, logs, or other secrets
inside the staged bundle.

## Copy/install model

For now the bundle is portable: copy the whole `bin/windows-x64/` directory to
the target machine/location. Keep the four TaskTrack executables and
`tunnel-client.exe` together.

For a local coding-agent MCP connection, register `TaskTrackMcp.exe` from that
directory. For ChatGPT tunnel access, launch `TaskTrackTunnelGui.exe`.

A future installer can consume this staged directory; installer technology
should not change the runtime/package boundary.
